## Why

The modern rendering tier emits a spurious `CYLINDER draw GL error: 1282` (`GL_INVALID_ENUM`) warning on radeonsi (and under xvfb). The cylinder draw is innocent: sticky `GL_INVALID_ENUM` errors set by legacy fixed-function / `GL_*_EXT` OpenGL calls in the shared `GLWidget::initializeGL()` — code dating to a Mesa 6.5.3 workaround — are drained by the modern backend's only post-draw `glGetError()` check and mislabeled as coming from the cylinder draw. Rendering is unaffected (98.96% parity vs legacy, PSNR ~36 dB), but a real error being generated and queued can mask genuine draw-path errors.

## What Changes

- Remove or profile/guard-support-check the legacy OpenGL calls in `GLWidget::initializeGL()` that are invalid on the resolved GL 3.3 context (`GL_COLOR_SUM_EXT`, `GL_LIGHT_MODEL_COLOR_CONTROL_EXT`/`GL_SEPARATE_SPECULAR_COLOR_EXT`, and, if the context is core, the fixed-function lighting block `GL_LIGHTING`/`GL_LIGHT0`/`glLightfv`).
- Ensure the modern backend's draw-path error reporting reflects only errors produced by its own draw calls, so a stale error from shared init cannot leak into or be attributed to a sphere/cylinder/line draw.
- No changes to rendered output; visual parity with the legacy backend is preserved.

## Capabilities

### Modified Capabilities

- `gpu-rendering-pipeline`: add a requirement that the modern tier's GL error inspection reports only errors generated by its own draw calls (stale errors from shared context init must not surface or be misattributed), and that shared GL context initialization does not introduce invalid-enumeration errors on the 3.3 context.

## Impact

- `libavogadro/src/glwidget.cpp` — `GLWidget::initializeGL()` legacy init block.
- `libavogadro/src/rendering/modernbackend.cpp` — `drawInstances()` error check (the surfacing point, not the source).
- `libavogadro/src/global.h` — fallback `#define`s for the removed EXT enums (may become unused).
- `libavogadro/tests/parityharness.h` — repeats the same `glLightModeli` EXT call; consider whether tests need the same treatment.
- Depends on confirming the actually-resolved context profile (core vs compatibility), which sets the exact scope of invalid calls.
